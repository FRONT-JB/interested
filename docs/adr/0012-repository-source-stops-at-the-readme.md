# 저장소 Source의 원문은 README와 저장소 신원까지다

GitHub 저장소를 Source로 다룰 때 원문으로 읽는 것은 README 본문과 저장소 신원(최근 릴리스, topics, 주 언어, 라이선스, 개설일, 마지막 push, 별 수)까지다. 코드·CHANGELOG·이슈·PR·릴리스 노트는 그 주소 안에 있지만 원문이 아니고, 못 읽은 것으로 밝힌다.

저장소는 앞의 세 유형과 다르다. 영상은 자막이, 글은 본문이, X는 글 하나가 원문의 자연스러운 경계를 이미 갖고 있다. 저장소는 그 경계가 없어서 URL 하나가 수천 개의 파일을 가리킨다. 어디까지 읽을지를 정하지 않으면 매번 다른 기준으로 읽게 되고, 그렇게 쌓인 Note들은 같은 유형인데 서로 다른 것을 요약한 것이 된다.

README에서 멈추는 것은 [ADR-0003](./0003-note-does-not-replace-the-source.md)의 연장이다. 저장소 전체를 읽어 정리하면 그 결과물은 저장소의 보완재가 아니라 대체재에 가까워지고, Note가 원문을 대신하지 않는다는 선이 무너진다.

저장소 신원을 원문에 포함하는 것은 반대 방향의 이유다. README는 저장소가 **자기에 대해 하는 말**이라, 그것만 읽으면 자기소개를 검증할 자리가 없다. 유튜브에서 자막의 고유명사를 `meta.keywords`와 대조하듯([references/source-limits.md](../../.claude/skills/study-source/references/source-limits.md)), 저장소는 개설일과 마지막 push가 README의 이력 서술을 대조한다. 실제로 activegraph의 README는 v0부터 v1.10까지의 이력을 적는데 저장소 `created_at`은 2026-05-16이다 — README만 읽어서는 보이지 않는 대비다.

## Considered Options

- **README만 읽는다** — 손이 가장 적게 간다. 스크립트가 이미 하고 있는 것에 「못 읽은 것」만 채우면 끝난다. 다만 README의 자기소개를 검증할 자리가 끝까지 생기지 않아서, 「눈에 걸린 자리」가 README 안의 앞뒤 대비로만 좁아진다.
- **저장소 전체를 읽는다** — 파일 트리·CHANGELOG·이슈까지 긁는다. 원문이 무한히 커져 덩어리 상한(ADR-0009)이 성립하지 않고, ADR-0003이 피하려던 자리로 정확히 들어간다.

## Consequences

- **저장소 Source에서 `missing`은 늘 비어 있고, 그것은 거짓이다.** `fetch_source.py`는 저장소 URL을 `web`으로 처리하고 본문을 얻으면 못 읽은 것이 없다고 보고한다. 코드·이슈·CHANGELOG를 통째로 안 읽었는데 `[]`가 온다. 스킬은 이 값을 믿지 않고 `source-limits.md`의 저장소 줄을 읽어 「못 읽은 것」을 채운다.
- **저장소 신원은 브리핑의 `Source` 헤더에 산다.** `[원문]` 라벨을 붙이지 않는다. 라벨은 무엇으로 검증되는지의 표시이고 `[원문]`의 대조 원본은 `text.txt`인데, 신원은 그 파일에 없어서 인용으로 적으면 결정적 검사에 걸린다. 헤더는 원문이 **한 말**이 아니라 그 원문이 **무엇인지**를 적는 자리라 라벨이 없다.
- **README 안의 링크는 주소를 잃는다.** 본문 추출이 링크 텍스트만 남기므로, README가 가리키는 문서 사이트·논문·형제 저장소는 이름만 남고 URL이 사라진다. 그것들을 확인하려면 5-1의 「모르는 것」으로 올려 사람이 고르게 한다.
- **이 선은 저장소 루트에만 적용된다.** 이슈 하나는 여러 사람이 시간 순으로 주고받은 기록이라 X 스레드에 가깝고, 못 읽은 것도 「코드」가 아니라 「이어지는 댓글」이 된다. 같은 절차로 덮으면 둘 다 어설퍼진다.
