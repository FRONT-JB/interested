# Source 하나를 읽고 Note 한 편 쓰기

용어는 [CONTEXT.md](../../../CONTEXT.md)의 정의를 그대로 쓴다 — Source, Note, Take, Concept.

이 스킬은 두 가지를 한다. **원문을 사람이 제대로 쥘 수 있게 펼쳐 보이고**, 그 위에서 **사람의 관점을 받아 Note로 조립한다.** 앞의 것을 소홀히 하면 뒤의 것이 빈다 — 원문을 얕게 쥔 사람에게 "여기서 뭐가 새로웠나"를 물으면 얕은 답이 오고, 그 답이 그대로 발행된다.

## 이 스킬이 하지 않는 것

[ADR-0004](../../../docs/adr/0004-the-skill-does-not-invent-the-perspective.md)가 이 스킬의 헌법이다.

- **관점을 지어내지 않는다.** "여기서 뭐가 새로웠나", "어디에 쓸 생각인가", "믿기지 않는 대목은"에 대한 답은 사람 것이다. 원문에서 그럴듯한 문장을 뽑아 그 자리를 채우면 Concept 그래프가 "내 관심의 궤적"이 아니라 "그럴듯하다고 판단된 것의 궤적"이 된다.
- **질문 단계를 건너뛰지 않는다.** 초안 생성은 한 번의 호출이 아니라 대화다. 느려 보이는 것은 비효율이 아니라 이 저장소가 성립하는 조건이다. 사람이 "알아서 써줘"라고 해도 질문은 던진다.
- **되물을 자리를 고쳐서 넘기지 않는다.** 게이트가 되묻자고 하면 초안을 보여주지 않는다. 반쯤 쓴 문장을 먼저 보여주면 사람이 고치는 대상이 백지가 아니라 기계가 쓴 문장이 되고, 그때부터 관점은 기계 것이다.
- **확인하지 못한 것을 확인한 것처럼 적지 않는다.** 브리핑이 두꺼워진 만큼 지어낼 자리도 늘었다. 대조되지 않는 문장은 브리핑에서 빼고 못 읽은 것으로 내린다.

원문의 뼈대를 Note 본문에 싣는 것은 [ADR-0009](../../../docs/adr/0009-the-note-carries-the-sources-outline.md)가 허락한 만큼까지다 — 최대 7덩어리, 열 문장 안팎. 그 이상은 [ADR-0003](../../../docs/adr/0003-note-does-not-replace-the-source.md)의 철회이고, 저작권상의 위치와 이 저장소의 차별점을 동시에 잃는다. 7은 상한이지 목표가 아니라서, 짧은 원문은 두세 덩어리로 끝난다.

## 절차

브리핑을 짓고 답을 받는 데 3~6단계를 쓰고, Note를 쓰는 데 7~11단계를 쓴다.

### 1. 중복 Source를 먼저 본다

링크를 받으면 원문을 열기 전에 이미 쓴 Note인지 본다. Source가 Note의 식별자라서, 같은 URL로 두 편을 쓰면 한 원문이 Concept 그래프에서 두 번 센다.

```bash
node --input-type=module -e '
import { readRepository } from "./packages/core/src/repository/read.ts";
import { findDuplicateSource } from "./packages/core/src/note/duplicate.ts";

const source = process.argv[1];
const { notes, concepts } = await readRepository(process.cwd());
const duplicate = findDuplicateSource({ source, notes });

console.log(JSON.stringify({
  duplicate,
  vocabulary: concepts.map(({ concept }) => concept),
}, null, 2));
' "<링크>"
```

`duplicate`가 나오면 거기서 멈추고 사람에게 알린다 — 이미 쓴 Note의 경로와 제목을 보이고, 새로 쓸지 그 Note를 고칠지 묻는다. 임의로 진행하지 않는다.

`vocabulary`는 8단계에서 게이트에 넘길 기존 Concept 어휘다. 여기서 받아 들고 있는다.

### 2. Source를 통째로 가져온다

```bash
python3 .claude/skills/study-source/scripts/fetch_source.py "<링크>" --out /tmp/source
```

URL 유형을 스스로 가려 유튜브면 메타·설명·챕터·자막을, 블로그면 본문을, X면 글을 JSON 하나로 내놓는다. 자막과 본문 전문은 `--out` 디렉터리에 `transcript.txt` · `text.txt`로 떨어지므로 **그 파일을 통째로 읽는다.** 앞부분만 훑고 브리핑을 지으면 뒤쪽 절반이 통째로 빠진 요지가 나온다.

`WebFetch`를 먼저 쓰지 않는다. WebFetch는 작은 모델이 페이지를 읽고 질문에 답해 주는 도구라 돌아오는 것이 원문이 아니라 그 모델의 요약이고, 요약의 요약을 재료로 삼으면 사람이 "여기가 걸린다"고 짚을 대목이 이미 깎여 나간 뒤다. 스크립트가 `ok: false`를 내거나 유형을 못 잡는 자리에서만 WebFetch로 보완한다.

**`missing`과 `diagnostics`를 반드시 읽는다.** 못 읽은 것이 여기 들어온다 — 자막 없는 영상, 280자에서 잘린 X 글, 로그인이 막은 본문. 조용히 넘기면 사람은 기계가 원문을 다 읽은 줄 알고 답하게 되고, 그 답으로 쓴 Note는 읽지도 않은 것에 대한 판단이 된다.

읽지 못한 것이 있어도 멈추지 않는다. 무엇을 못 읽었는지 밝힌 채로 답하는 것은 사람이 할 수 있는 선택이다. 유형별로 무엇을 못 가져오는지는 [references/source-limits.md](references/source-limits.md)에 있다.

#### 2-1. 저장소는 신원을 따로 가져온다

링크의 호스트가 정확히 `github.com`이고 경로 조각이 **둘**이면(`github.com/{owner}/{repo}`) 스크립트 결과에 더해 저장소 신원을 가져온다. `gist.github.com`과 `raw.githubusercontent.com`은 조각이 둘이어도 호스트가 달라 여기 들지 않는다. 스크립트는 저장소를 블로그와 같은 `web`으로 처리해 README 본문만 주고, README는 저장소가 자기에 대해 하는 말이라 그것만으로는 대조할 자리가 없다 ([ADR-0012](../../../docs/adr/0012-repository-source-stops-at-the-readme.md)).

```bash
gh api repos/{owner}/{repo} --jq '{
  full_name, description, homepage, language, topics, license: .license.spdx_id,
  stars: .stargazers_count, forks: .forks_count, open_issues: .open_issues_count,
  created_at, pushed_at, archived
}'
```

`gh`가 없거나 인증이 풀렸으면 익명으로 물러선다 — `curl -s https://api.github.com/repos/{owner}/{repo}`. 공개 저장소는 같은 값이 오고 차이는 시간당 한도(5,000 대 60)와 비공개 저장소뿐이다. **어느 경로로 왔는지 밝힌다.** 익명으로 왔다면 비공개 저장소일 때 404가 나는데, 그건 "저장소가 없다"와 구분되지 않는다. 둘 다 실패하면 신원을 못 읽은 것으로 내리고 README만으로 간다.

받은 것은 브리핑의 `**Source**` 헤더에 싣는다. **`[원문]` 라벨을 붙이지 않고 인용으로 적지 않는다** — `[원문]`의 대조 원본은 `text.txt`인데 신원은 거기 없어서 4-1의 검사에 걸린다. 헤더는 원문이 한 말이 아니라 그 원문이 무엇인지를 적는 자리라 라벨이 없다.

```
**Source** — [{owner}/{repo}]({링크}) (README {n}자 · {language} · {license} · {created_at 연월} 개설, {pushed_at 연월} 마지막 push · ★{stars})
```

제목 자리가 `owner/repo`라 글쓴이를 따로 적지 않는다. 유튜브 헤더의 `{채널·글쓴이}`에 해당하는 것이 이미 제목 안에 있다.

**받은 것을 전부 헤더에 넣지 않는다.** `topics`·`homepage`·`forks`·`open_issues`는 헤더에 안 싣고 손에 들고 있는다 — 유튜브의 `meta.keywords`가 헤더에 안 들어가고 자막의 고유명사를 대조하는 데만 쓰이는 것과 같다. README가 이름을 흐리게 지나간 자리를 `topics`로 대조하고, 5-1의 「모르는 것」을 고를 때 `homepage`가 이미 답인 항목을 걸러 낸다. `archived`가 참이면 그때는 헤더에 적는다 — 보관된 저장소라는 사실은 README가 말해 주지 않는다.

신원이 README를 대조하는 자리는 `### 눈에 걸린 자리`다. 「README는 v0부터의 이력을 적는데 저장소는 2026-05에 만들어졌다」처럼 **사실끼리의 대비**까지가 그 절의 범위이고, 그 이상은 사람이 답할 자리다 ([references/briefing-format.md](references/briefing-format.md)).

**`missing`이 비어서 오는데 그것은 거짓이다.** 저장소에서 스크립트는 못 읽은 것이 없다고 보고한다. 코드·이슈·CHANGELOG를 통째로 안 읽었는데 그렇다. 그 값 대신 [references/source-limits.md](references/source-limits.md)의 저장소 줄을 「못 읽은 것」에 옮긴다.

**루트가 아닌 GitHub URL은 이 절차를 타지 않는다.** 이슈·PR·gist·특정 파일은 지금처럼 `web`으로 다루되, **그렇게 다룬다는 것을 브리핑에 밝힌다.** 이슈 하나는 여러 사람이 시간 순으로 주고받은 기록이라 못 읽은 것도 「코드」가 아니라 「이어지는 댓글」이고, 밝히지 않으면 블로그 글처럼 조용히 처리된다.

### 3. 브리핑을 짓는다

아직 보이지 않는다. 4단계의 검증을 지난 것만 5단계에서 보인다. 사람에게 보이는 것은 그 한 번이다.

**원문이 영어여도 브리핑은 한글로 쓴다.** 다만 `harness`, `context engineering`처럼 원문이 이름으로 쓰는 기술 용어는 옮기지 않고 그대로 둔다 — 번역해 두면 나중에 Concept 이름을 정할 때 원문과 이어 붙지 않는다.

**브리핑과 질문도 평서체로 쓴다.** 묻는 말투가 답하는 말투를 끌고 가서다. 경어체로 물으면 경어체로 답이 오고, 그 답이 그대로 `harvest`·`application`·`doubt`가 되어 게이트가 경어체를 고치게 되는데, 게이트는 세 자리에서 틀리게 고친다. 평서체로 물으면 그 교정이 애초에 필요 없다.

형식과 각 절을 어떻게 채우는지는 [references/briefing-format.md](references/briefing-format.md)에 있다. **거기를 읽고 짓는다.** 요약하면 이렇다.

| 절 | 라벨 | 무엇이 들어가나 |
|---|---|---|
| 원문이 한 말 | `[원문]` | 원문을 덩어리로 묶어 각 1~2문장. 덩어리마다 타임스탬프나 위치를 단다 |
| 원문에서 | `[원문]` | 원문 그대로의 인용 2~4개와 한글 번역 |
| 쉽게 풀면 | `[에이전트]` | 앞의 두 절을 처음 보는 사람도 알아듣게 푼 것 |
| 모르는 것 | — | 원문이 설명 없이 지나간 이름·도구·개념 목록 (5-1로 넘어간다) |
| 눈에 걸린 자리 | `[원문]` | 원문 안에서 확인되는 사실과 사실끼리의 대비 |
| 못 읽은 것 | — | 2단계의 `missing` |

라벨이 이 브리핑의 뼈대다. `[원문]`은 자막이나 본문으로 대조되는 것이고 `[에이전트]`는 내가 보태는 것이라, 섞이면 사람이 무엇을 믿을지 고를 수 없게 된다.

**우선순위는 번역 → 요약 → 풀이다.** 시간이나 분량이 모자라면 풀이를 먼저 줄인다. 원문이 실제로 한 말이 남고 내 설명이 빠지는 쪽이, 반대보다 낫다.

### 4. 브리핑을 검증한다

**브리핑은 파일로 짓는다.** `/tmp/briefing-{식별자}.md`에 쓰고, 아래 단계에는 그 경로만 넘긴다. 브리핑 본문을 대화에 되풀이해 붙이면 검사·감사·수정마다 같은 글이 문맥에 다시 쌓인다. 사람에게 보이는 것은 5단계에서 한 번이다.

**4-1. 결정적 검사를 돌린다.** 인용이 원문에 실제로 있는지, 덩어리의 시각이 원문 길이 안인지, 조사 문장에 링크가 붙었는지를 코드가 본다.

```bash
node .claude/skills/study-source/scripts/audit_briefing.mjs \
  /tmp/briefing-{식별자}.md /tmp/source/transcript.txt 1159
```

인용·시각·링크는 스크립트가 브리핑에서 직접 뽑는다. **`claims` 배열을 손으로 만들지 마라** — 브리핑을 문맥에 통째로 한 번 더 올리는 일이고, 그러려고 `briefing.ts` 소스를 읽으러 갈 이유도 없다. 셋째 인자(원문 길이, 초)는 시각이 없는 글이면 뺀다.

**4-2. 풀이를 감사에 넘긴다.** 결정적 검사가 못 보는 것이 하나 남는다 — 풀이가 원문을 오독했는지다. 이건 내가 다시 읽어서는 못 잡는다. 같은 독해를 두 번 하는 것이기 때문이다.

그래서 **깨끗한 문맥의 서브에이전트**에 넘긴다. `subagent_type`은 `study-source-auditor`이고, 넘기는 것은 이 대화의 맥락이 아니라 **파일 경로 둘**이다.

> 원문: `/tmp/source/transcript.txt`
> 브리핑: `/tmp/briefing-{식별자}.md`

무엇을 어떻게 볼지는 그 에이전트 정의(`.claude/agents/study-source-auditor.md`)가 갖고 있다. 프롬프트를 여기에 다시 적지 않는다 — 두 곳에 두면 한쪽만 고쳐진다.

그 에이전트는 Haiku에 박아 뒀다. 감사는 대조할 원본이 손에 있고 할 일이 한정된 작업이라 상위 모델이 필요 없고, 실측에서 Haiku가 Opus·Sonnet이 놓친 자리까지 잡았다. 바꿀 일이 생기면 그 파일의 `model:` 한 줄만 고친다.

**띄웠으면 상태를 확인하러 가지 않는다.** 목록을 훑거나 잠깐 자면서 되돌아보는 턴은 결과를 앞당기지 않고 문맥만 늘린다. 결과는 알아서 온다.

**다만 여기서 끝내지 마라.** 감사 결과를 받는 것이 이 단계의 끝이 아니라 시작이다. 결과를 받으면 브리핑을 한 번 다시 쓰고, 5단계로 가서 사람에게 보이고 세 질문까지 던져야 한 번의 실행이 끝난다. "결과를 기다린다"고 말하고 멈춘 실행은 사람에게 아무것도 남기지 않는다 — 실측에서 실제로 그렇게 끝난 적이 있다.

**걸린 것은 고치지 않고, 한 번에 내린다.** 감사 결과를 **전부 받은 뒤 브리핑을 한 번만 다시 쓴다.** 건마다 고치면 브리핑이 그 횟수만큼 문맥에 다시 올라간다. 걸린 문장은 빼고 "확인 못 한 것"에 모은다 — 고쳐서 내보내면 원문의 말도 브리핑의 말도 아닌 문장이 남는다 ([ADR-0008](../../../docs/adr/0008-the-observers-prose-is-written-by-a-model.md)).

**원문이 짧으면 4-2를 건너뛴다.** 대략 5,000자 미만이면 사람이 원문을 직접 훑을 수 있고, 인용은 4-1이 이미 지킨다. 감사는 사람이 원문을 통째로 다시 읽기 어려울 때를 위한 장치다.

### 5. 브리핑을 보이고, 한 번에 묻는다

검증을 지난 것만 보인다. 마지막 두 줄에 못 읽은 것과 확인 못 한 것을 적는다.

```
*못 읽은 것 — {missing}*
*확인 못 한 것 — {감사에 걸려 내린 것, 검색으로 못 찾은 것}*
```

둘 다 비었으면 그 줄은 없다. 있는데 안 적는 것이 이 스킬이 할 수 있는 가장 나쁜 일이다.

**브리핑 다음에 두 가지를 한 번에 붙인다** — 모르는 것 목록과 세 질문이다.

순서가 중요하다. 예전에는 브리핑을 보이기 **전에** 조사할 것을 고르라고 물었는데, 그러면 사람은 아직 읽지도 않은 글에 대해 "뭐가 궁금한지" 답해야 한다. 실제로 "정리한 걸 보여줘야 알지"라는 말을 들은 자리다. 무엇이 궁금한지는 읽고 나서 정해진다.

#### 5-1. 모르는 것을 카테고리로 묶어 보인다

원문이 설명 없이 지나간 이름·도구·개념을 모아 던지고, 어느 것을 조사할지 사람이 고르게 한다. 전부 조사하면 브리핑이 원문보다 길어지고, 아무것도 조사하지 않으면 원문의 전제가 빈 채로 남는다.

목록이 평평하면 열 개를 하나씩 훑어야 해서 고르는 일 자체가 부담이 된다. **성격이 같은 것끼리 묶되 이름은 다 보인다.**

```
원문이 설명 없이 지나간 것이 이만큼이다. 조사해 붙일 것이 있으면 골라 달라 —
번호로 집어도 되고 「받아쓰기 도구 전부」처럼 묶음째로 골라도 된다. 없으면 없다고 해도 된다.

**받아쓰기 도구** — 1. Handy  2. Voice Ink  3. WhisperFlow
**에이전트 harness·자동화** — 4. Warp  5. oz.dev  6. Codex 앱의 automations  7. Exa
**개념과 출처** — 8. Karpathy의 gist  9. Obsidian headless CLI
**사람** — 10. Adam Neely
```

카테고리는 미리 정해 두지 않는다. 이 Source가 무엇을 안 짚고 지나갔는지에 따라 매번 다르게 묶인다. 묶음이 하나뿐이면 굳이 제목을 달지 않는다.

**카테고리째 고르는 것은 사람의 선택이지 기본값이 아니다.** 묶음 하나에 여섯 개가 들어 있으면 검색도 여섯 번이다. 사람이 그렇게 고르지 않는 한 항목 단위로 조사한다.

#### 5-2. 세 질문을 같이 던진다

1. **여기서 뭐가 새로웠나** — 이미 알고 있던 것과 어디가 달랐나
2. **어디에 쓸 생각인가** — 지금 붙잡고 있는 코드나 결정 중 어디에 닿나
3. **믿기지 않는 대목은** — 원문이 너무 쉽게 넘어갔다고 느낀 곳이 어디였나

브리핑에서 얻은 맥락으로 질문을 이 Source에 맞게 구체화해도 된다. 질문의 수를 줄이거나 답을 예시로 채워 보이는 것은 안 된다 — 예시가 곧 답이 된다. 브리핑의 관찰을 질문에 얹는 것도 여기까지다. "여기가 걸리지 않나"는 이미 답이다.

#### 5-3. 답을 받는다

**조사할 것을 골랐으면 먼저 조사해 보인다.** 서브에이전트에 항목 목록을 주고 **문장 하나와 링크 하나씩만** 돌려받아 브리핑의 `### 원문 밖에서 확인한 것`에 붙이고, 그것까지 읽은 뒤에 세 질문에 답하게 한다. 조사가 답하는 데 도움이 되라고 있는 것이라, 답을 받은 뒤에 조사하면 늦다.

> 아래 항목을 각각 웹에서 확인하고, 항목마다 한 문장과 근거 링크 하나만 돌려 달라.
> 검색으로 확인되지 않은 항목은 지어내지 말고 "확인 못 함"이라고 답해라.
> 설명을 길게 쓰지 마라. 한 문장을 넘기면 브리핑에 실을 수 없다.

검색을 직접 하지 않는다. 검색 결과는 한 건이 브리핑에 남는 한 문장보다 수십 배 길고, 한 번 문맥에 들어오면 그 뒤 모든 턴이 그것을 다시 읽는다. 자동 자막은 고유명사를 자주 틀리므로([references/source-limits.md](references/source-limits.md)), 이름을 서브에이전트에 넘기기 전에 메타데이터와 대조한다.

**고를 것이 없다고 하면 그대로 답을 받는다.** 대부분이 이쪽이고, 그러면 왕복 한 번으로 끝난다.

### 6. Take를 확인받는다

답을 받으면 **Take 한 문장**을 사람의 답에서 뽑아 확인받는다. Take는 원문의 주장이 아니라 내 수확이다. 제목과 Concept 이름도 이때 함께 확인받는다 — 셋을 따로 물으면 왕복이 셋으로 늘어난다.

이름이 관점을 담는 자리라 여기만은 왕복을 줄이지 않는다 ([ADR-0001](../../../docs/adr/0001-note-connects-through-concept.md)). 기존 어휘에 뜻이 같은 것이 있으면 새 이름을 만들지 말고 그것을 쓴다.

### 7. 초안 재료를 모은다

`NoteDraft` 한 덩어리로 모은다.

| 자리 | 어디서 오나 |
|---|---|
| `source` | 1단계에서 받은 링크 |
| `title` | 원문이 던진 질문 형태로 짓는다. 사람에게 확인받는다 |
| `date` | 오늘 (`YYYY-MM-DD`) |
| `take` | 6단계에서 확인받은 한 문장 |
| `concepts` | 이 Note가 다루는 Concept. 1단계의 `vocabulary`를 먼저 보고 이미 있는 이름이면 그것을 쓴다 |
| `sourceClaim` | 브리핑의 **원문의 주장** 세 문장 |
| `sourceOutline` | 브리핑의 **원문이 한 말** 덩어리들. 라벨과 타임스탬프를 떼고 문장만. 두 문장짜리 덩어리는 한 문장으로 줄여 전체를 열 문장 안팎으로 맞춘다 (ADR-0009) |
| `harvest` | 질문 1의 답 |
| `application` | 질문 2의 답 |
| `doubt` | 질문 3의 답 |

`harvest` · `application` · `doubt`는 사람의 답을 그대로 옮긴다. 문장을 다듬는 것은 9단계에서 하고, 여기서는 내용을 보태지 않는다.

**브리핑의 나머지는 넘어가지 않는다.** `쉽게 풀면`도 `원문에서`의 인용도 `원문 밖에서 확인한 것`도 Note에 실리지 않는다. 이것들은 사람이 질문에 답하려고 읽은 것이고, 발행되는 것은 Note다.

### 8. 게이트에 넣는다

```bash
node --input-type=module -e '
import { judgeDraft } from "./packages/core/src/note/rubric.ts";

const { draft, vocabulary } = JSON.parse(process.argv[1]);

console.log(JSON.stringify(judgeDraft({ draft, vocabulary }), null, 2));
' "$(cat /tmp/draft.json)"
```

판정은 두 갈래고, 갈래마다 할 일이 다르다.

**`outcome: "ask-back"`** — 재료가 모자란다. `corrected`가 아예 없다.

- `askBack[].question`을 사람에게 그대로 던진다. 답을 다시 받아 7단계로 돌아간다.
- **초안을 보여주지 않는다.** 조립한 문장도, 고칠 수 있었던 형식도 꺼내지 않는다.
- 답을 대신 채우거나 문턱을 넘길 만큼만 늘려 쓰지 않는다.
- `field`가 `concepts`면 게이트가 이름을 하나도 확정하지 못한 것이다. `vocabulary`를 보고 **영어 이름을 정해** 7단계로 돌아간다. 기존 어휘에 뜻이 같은 것이 있으면 새 이름을 만들지 말고 그것을 쓴다 ([ADR-0001](../../../docs/adr/0001-note-connects-through-concept.md)). 이름이 관점을 담는 자리이므로 사람에게 확인받는다.
- `field`가 `sourceOutline`이면 덩어리가 일곱을 넘은 것이다. 어느 덩어리를 합칠지 사람에게 묻는다.
- `reason`에 "관점보다 길다"가 있으면 원문 정리가 관점을 눌렀다는 뜻이다. **요약을 줄여서 통과시키지 않는다** — 그건 문턱을 넘기려고 재료를 깎는 것이다. 관점을 더 받는 쪽으로 되묻는다.
- 게이트의 판정이 틀렸다고 보이면 — 짧지만 날카로운 답이 걸렸다면 — 사람에게 그렇게 말하고 판단을 받는다. 게이트를 우회하는 것도 사람의 결정이다.

**`outcome: "pass"`** — `corrected`를 쓰고 `corrections`는 한 줄로 알린다.

- 경어체 교정과 Concept slug 교정은 되묻지 않고 이미 반영돼 있다. 무엇을 고쳤는지는 알리되 승인을 구하지 않는다.
- `after`가 `null`인 `corrections` 항목은 게이트가 이름을 확정하지 못하고 지운 Concept이다. 한글이 섞였거나(`React 서버 컴포넌트`) 영숫자로 옮길 수 없는 기호가 있는(`c++`) 이름이다. **게이트는 이런 이름을 깎아 내지 않는다** — `react`나 `c`로 줄이면 뜻이 다른 Concept이 조용히 굳기 때문이다. 지워진 자리마다 `vocabulary`를 보고 영어 이름을 정해 `concepts`에 다시 넣고 게이트를 다시 돌린다.
- **`corrections`의 `after`를 그대로 믿지 마라.** [references/gate-corrections.md](references/gate-corrections.md)를 보고, 걸리는 문장은 9단계에서 손으로 맞춘다.

### 9. 본문을 조립한다

`corrected`의 재료로 본문을 쓴다. 형식은 [notes/2026-07-08-parameter-object-pattern-js.md](../../../notes/2026-07-08-parameter-object-pattern-js.md)를 따르되, `## 원문이 한 말`이 그 사이에 들어간다.

```
{sourceClaim — 원문이 무슨 말을 하는지. 한 문단, 짧게}

## 원문이 한 말

{sourceOutline — 덩어리마다 한 줄씩. 목록이 아니라 이어지는 문단으로 쓴다}

## 내가 건진 것

{harvest — 원문의 결론이 아니라 내 수확이 무엇인지}

## 어디에 쓸 생각인가

{application}

## 미심쩍은 대목

{doubt}
```

- 평서체 1인칭이다. "~라고 본다", "내가 건진 것은".
- `## 원문이 한 말`은 기계가 원문에서 뽑은 것이고 나머지는 사람의 말이다. 이 절에 사람이 하지 않은 판단을 섞지 않는다 — "이 대목이 핵심이다" 같은 말은 여기 자리가 없다.
- 8단계의 표에 걸린 문장을 여기서 맞춘다. `닿다` → `닿는다`, `보이다` → `보인다`.
- 관점 문단에 사람이 말하지 않은 근거·사례·수치를 보태지 않는다. 문장을 잇고 다듬는 데까지다.
- 관련 Note로 가는 링크를 넣지 않는다. 관련성은 Concept을 거쳐 렌더링 시점에 계산한다 ([ADR-0001](../../../docs/adr/0001-note-connects-through-concept.md)).

### 10. 파일로 쓴다

경로는 `notes/{date}-{slug}.md`다. `slug`는 제목에서 사람이 알아볼 만한 영문 소문자 몇 단어로 줄인다 (`2026-07-08-parameter-object-pattern-js.md`).

```bash
node --input-type=module -e '
import { noteFrontmatterSchema } from "./packages/core/src/note/schema.ts";
import { renderMarkdown, writeMarkdown } from "./packages/core/src/repository/write.ts";

const { draft, body, path } = JSON.parse(process.argv[1]);
const { source, title, date, take, concepts } = draft;
const frontmatter = noteFrontmatterSchema.parse({ source, title, date, take, concepts });

const outcome = await writeMarkdown({
  root: process.cwd(),
  path,
  contents: renderMarkdown({ frontmatter, body }),
});

console.log(JSON.stringify(outcome));
' "$(cat /tmp/note.json)"
```

- `fs.writeFile`을 직접 부르지 않는다. 저장소에 파일을 쓰는 이음매는 `writeMarkdown` 하나다.
- `noteFrontmatterSchema.parse`가 던지면 그건 게이트를 통과했어도 형식이 어긋났다는 뜻이다. 메시지를 보고 고쳐 다시 돌린다.
- `{ kept: ... }`가 나오면 그 경로에 파일이 이미 있어 손대지 않은 것이다. 덮어쓰지 말고 사람에게 알린다.

### 11. 마무리

쓴 경로, 확정된 Concept, 게이트가 고친 것, 브리핑에서 내린 것을 한 번에 보인다. `pnpm concepts`로 이 Note가 어떤 Concept을 3회에 가깝게 밀어 올렸는지 볼 수 있다 ([ADR-0002](../../../docs/adr/0002-concept-promotion-at-three.md)).

커밋은 하지 않는다. 발행 전에 사람이 문장을 고친다.

## 게이트가 판정하는 것과 못 하는 것

게이트(`packages/core/src/note/rubric.ts`)는 순수 함수다. 저장소를 읽지 않고, 넘겨받은 재료와 어휘만 본다.

확정적으로 판정하는 것 — Concept slug 형식, 기존 어휘와의 대조, `sourceOutline`의 덩어리 수.

반쯤만 확정적인 것 — 경어체 교정. 검출은 확정적이지만 교정은 동사·형용사 구분에서 갈려 틀리게 고치는 자리가 남는다.

근사로 판정하는 것 — "관점이 얇다"는 글자 수로, "Take가 원문 요약이다"는 어휘 겹침으로, "원문 정리가 관점보다 길다"는 글자 수 비교로 재는 기계적 근사다. 짧고 날카로운 답을 되묻게 만들 수 있고, 길게 늘여 쓴 빈 말은 통과시킨다. 애매하면 되묻는 쪽으로 기울여 있으며, 최종 판단은 이 대화에서 사람과 에이전트가 한다.

브리핑 검사(`packages/core/src/source/briefing.ts`)도 순수 함수다. 자막에 없는 인용, 원문 길이를 넘는 시각, 링크 없는 조사를 잡는다. 풀이의 오독은 못 잡고, 그 자리는 4-2의 감사가 진다.

게이트를 자동 교정 쪽으로 옮기고 싶어질 때가 온다. 그건 개선이 아니라 ADR-0004의 철회다.
