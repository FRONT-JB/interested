에이전트 시스템의 진실 원천을 대화 기록이 아니라 append-only 이벤트 로그에 두고, 작업 그래프를 그 로그의 결정적 투영으로 만든다. 행동(behavior)들은 서로에게 말을 걸지 않고 공유 그래프의 변화에 반응하며, 모든 변경이 이벤트로 남으므로 재생·분기·구조 비교가 따라 나온다. 이 런타임의 자리는 제어 흐름을 모델링하는 워크플로 엔진 옆이 아니라 세계 상태를 모델링하는 쪽이다.

## 원문이 한 말

길게 도는 감사 가능한 에이전트 시스템을 위한 이벤트 소싱 반응형 그래프 런타임이라고 자신을 소개하고, 행동들이 서로 대화하는 대신 공유 그래프에 반응한다고 말한다. 채팅 기반 에이전트가 단체 대화라면 이쪽은 누가 무엇을 왜 바꿨는지 다 보이는 공유 작업공간이라고 비유한다. `pip install activegraph`와 `activegraph quickstart` 두 줄로, API 키도 설정도 없이 기록된 fixture 위에서 바이트 단위로 결정적인 출력을 먼저 보여준다고 말한다. 얻는 것으로 이벤트 소싱 그래프, 일급 반응형 행동, fork-and-diff, 팩, 격리된 이벤트 내보내기를 들고, 열두 개 primitive를 트레이스를 읽을 때 만나는 순서로 늘어놓는다. 행동의 실패는 예외가 아니라 `behavior.failed` 이벤트이며 예외는 런타임 진입점에만 산다고 적는다. 이벤트 타입은 런타임이 고정하지만 객체 타입과 관계 타입은 사용자가 고르는 문자열이라 중앙 스키마도 등록 절차도 없다고 말한다. 예제는 `depends_on` 엣지에 붙은 관계 행동으로, 조율 로직을 양쪽 끝점이 아니라 엣지 위에 두는 모양을 보인다. 채팅 프레임워크도 워크플로 엔진도 룰 엔진도 프로덕션 그래프 데이터베이스도 아니라고 선을 긋고, 마지막에 마법이 아니며 나쁜 행동은 나쁜 그래프를 만든다고 적는다. 팩 라이브러리와 프로덕션에서 도는 자체 호스팅 연구 에이전트를 형제 저장소로 두고 arXiv 논문 두 편을 설계 논거로 건다. v1.0이 2026년 5월에 나왔고 지금은 v1.10.0이며, 라이브 API 키나 라이브 HTTP가 있어야 통과하는 테스트는 들어올 수 없다고 말한다.

## 내가 건진 것

에이전트가 값을 기반으로 상태머신 같이 도는 경우 이 도구가 굉장히 유용하다는 생각이 들었다. 보통은 문서를 기반으로 레퍼런스를 만들어서 하나의 산출물로 여러 에이전트를 호출해 사용하는 방식을 썼는데, 무슨 일이 일어났었는지, 어떻게 작업했었는지, 더 나은 방법이 없었는지와 같이 그래프를 만들어서 과정을 돌려볼 수 있다는 것이 굉장히 좋은 방식이라고 봤다.

## 어디에 쓸 생각인가

하나의 harness 도구에서 end-to-end 과정을 이 도구로 그래프로 만들어 놓고 어느 지점에서 문제가 발생했는지 파악할 수 있을 것 같다. 더 나은 방법, 속도 개선 등 문제를 파악하는 것 외에 개선하는 데에도 쓸 수 있어 보인다. 「마법이 아니다. 나쁜 행동은 나쁜 그래프를 만든다. 런타임은 그 나쁨을 없애는 것이 아니라 들여다볼 수 있게 만든다」라는 문구가 이 도구의 모든 것을 말해준다고 본다.

## 미심쩍은 대목

그래프를 만들어서 의도와 다르게 동작했다거나 나쁜 그래프라는 것을 어떻게 판단할 수 있을까. 막연하게 이 도구를 사용해서 나쁜 지점을 찾았다고 해서 그게 진짜로 나쁜 지점이었을까, 아니면 원래 실행이 의도한 동작이었을까 판단하기가 어렵지 않나 싶기도 하다. 결과적으로는 이 도구를 맹신하는 것이 아니라 이 도구로 들여다보면서 이게 실제로 나쁜 과정이었는지, 다른 걸로 개선한다면 정말로 개선이 됐는지와 같이 볼 줄 알아야 한다고 생각했다.
